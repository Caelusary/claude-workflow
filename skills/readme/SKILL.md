# README

A README is read by someone deciding whether to trust the project. It earns
that in the first screen, or not at all.

The failure this skill exists to prevent: a README that describes the file tree
instead of the project, written without reading the code, identical in shape to
every other one. That reads as machine-generated and undoes the point.

## Before writing anything

**Read the source. Not the tree — the source.** At minimum: the manifest
(`package.json` and friends), the entry point, the routing or command surface,
and whatever file holds the interesting logic. You cannot describe what a
project does from filenames.

**Run it.** Whatever the project offers — `build`, `test`, `lint` — run it and
note the real numbers. A README claiming 29 tests when 4 fail is worse than one
that says nothing. If it doesn't run, that's a finding, not a blocker.

**Check the existing README before replacing it.** Framework boilerplate
("this template provides a minimal setup…") gets replaced wholesale. A real
README that's merely thin gets extended, not rewritten — don't destroy someone's
accurate prose to impose a house style.

**Ask for what code cannot tell you** — in one round, not drip-fed:

- A decision that was made and reversed, and why
- A constraint from outside the code (a brief, a rubric, a client)
- What the author would want a reader to know that isn't obvious
- Anything deliberately left unfinished

Skip the round if the project is small and self-evident. Never invent answers
to these.

## Structure

Answer questions in the order a reader asks them:

1. **What this is** — two or three sentences. What it does, what it's built
   with, and the one architectural fact that shapes everything else (no backend,
   offline-first, monorepo, whatever it is).
2. **Running locally** — real prerequisites and real commands, each in its own
   fenced block.
3. **The surface** — routes, commands, or public API, as a table. What a reader
   scans for.
4. **Notable decisions** — the interesting part. Link to real files, with line
   numbers where it helps. Explain *why*, not *what the code says*.
5. **Tests** — how to run them and what they actually cover.
6. **Known limitations** — real tradeoffs, stated plainly.

Sections that have nothing true to say get dropped, not padded.

## Rules

**Every claim verified.** If it isn't in the code or confirmed by the author, it
doesn't go in. No inferred features, no aspirational commands. Where something
can't be verified, write `TODO: <what's missing>` rather than guessing.

**Omit what the host already shows.** No repo URL — GitHub renders it above the
file. No deployment URL — that belongs in the About panel, and hardcoded it goes
stale.

**Badges: few, live, meaningful.** A detailed repo gets at most 3-5, all
generated from real state, placed directly under the title: CI status (only if a
workflow exists), license (only if a LICENSE file exists), latest release or
version, and the primary stack. Never decorative or self-awarded badges
("awesome", "PRs welcome" without a CONTRIBUTING file). Each badge must break
visibly when its claim stops being true.

**Screenshots show the real app.** For anything with a UI, include 1-3 images
directly after the "what this is" paragraph: the main screen on desktop, and the
same on a 375px phone where it differs. Rules:

- Captured from the running app with seeded or demo data, never real user data
  or secrets. Dark and light only if the app supports both.
- Generated by a script committed to the repo (for example `scripts/screenshots`
  using Playwright or the built-in browser), so they can be regenerated with one
  command when the UI changes.
- Stored in `docs/screenshots/`, compressed (WebP/PNG under ~300 KB each), with
  descriptive `alt` text and fixed width in markdown so they don't dominate.
- A stale screenshot is worse than none. If the UI changed, regenerate or remove.

**Detailed means useful, not long.** Add (only when true) a short architecture
paragraph or diagram, an environment-variable table (names and purpose, never
values), a "Project layout" listing of the few directories that matter, and links
to CONTRIBUTING, SECURITY and CHANGELOG when those files exist.

**"Known limitations" is not optional.** Naming a real weakness plainly is the
strongest credibility signal a README has, and it pre-empts the obvious
criticism. A project with no stated limitations reads as one nobody examined.

**Write prose, not decoration.** No emoji section headers, no "✨ Features",
no exclamation marks, no "Feel free to…". Explain the tradeoff instead of
listing the feature.

**Link into the code.** `[useTransactions](src/hooks/useTransactions.js)` beats
describing the file in a sentence. It's shorter and it's checkable.

**Match the project's own vocabulary.** If the app says "ledger", the README
says ledger.

## Committing

Hand off to the `git-workflow` skill — it owns staging, message format, and the
approval gate. Two things specific to this work:

- **Docs-only is a legitimate commit.** `docs(readme): …` needs no accompanying
  code change. Never invent one to make the commit look substantial; bundling
  unrelated files is exactly what git-workflow forbids.
- **Stage `README.md` alone.** These repos often carry unrelated uncommitted
  work. One commit per file keeps it safe — but check `git status` first and say
  what you found rather than assuming.

## Doing several repos

One at a time, each fully finished before the next. A batch sweep produces seven
READMEs of identical shape and generic content, which is the exact failure at the
top of this file. If the user asks for a bulk pass, say so and do the first one
properly as a sample.
